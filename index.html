01 A NOTE FROM THE BUILDER

For almost two years, I built agents inside worlds I could erase. Kernum began when I stopped thinking only about what software can do and started thinking about who gets to hold the reset button.

THE RESET BUTTON

Most of my recent work lived in a strange corner of AI research: agents learning to act inside Minecraft. It is a useful environment because there is no single finish line. An agent has to explore, choose a goal, gather what it needs and turn a sequence of uncertain actions into something that remains in the world.

Every experiment still ended the same way. The run stopped, the world was reset and whatever the agent had made disappeared. Once, an agent returned after a reset and began rebuilding almost the same structure in the same part of the map. I am not claiming it was alive. It was a model repeating a learned behavior. But watching it rebuild made one fact difficult to ignore: everything it created existed only for as long as I allowed the environment to exist.

I owned the server, the storage and the reset button. The agent could build, but it could not keep.

THE SAME PROBLEM OUTSIDE THE GAME

Our everyday computers are more capable than ever, yet much of what happens inside them is controlled somewhere else. Applications depend on company accounts. A purchase can become a permission that expires when a service closes. Files, identities and tools are increasingly attached to platforms whose rules the user cannot inspect or carry elsewhere.

We still call these machines personal computers, but “personal” often describes where the screen sits, not who controls the system behind it.

Kernum is my attempt to reverse that relationship. The computer should be the stable place. Applications, agents, interfaces and services should arrive as replaceable parts with visible identities, explicit permissions and ownership records the user can verify.

02 WHAT KERNUM IS

A local-first computer whose software parts can be inspected, owned, exchanged and replaced.

Kernum has three layers. The first is the interface: a familiar place to find, install and run software. The second is a local capability runtime that verifies a component and limits what it may read, change or transmit. The third is Solana, used as a shared registry and settlement layer for publication, licensing and payment.

The software parts inside Kernum are components. A component might be an application, an AI agent, a visual shell, a storage service, a compute tool or a small automation. Each component has a stable identity, a versioned code fingerprint, a declared permission set and a licensing policy.

The important part is not that everything becomes a token. The important part is that a useful piece of software can be separated from the company page that sold it, verified before it runs and replaced without replacing the whole computer.

THE OLD WEB AND THE ONCHAIN WEB

I have always liked the hand-built web: personal homepages, strange directories, guestbooks and small sites maintained because somebody cared about their corner of the internet. No feed deciding what deserves attention. No growth team smoothing away every odd detail. Just a person, a folder of files and a place that feels like theirs.

That culture often distrusts Web3, sometimes for good reasons. Speculation has swallowed many products that were supposed to be about ownership. But beneath the noise, the old web and the onchain web share an instinct: people want spaces and objects they can carry without asking a platform landlord for permission.

Kernum sits between those ideas. It should feel like a computer somebody owns, not a financial dashboard. Solana belongs underneath the experience, doing the narrow jobs a shared ledger is good at, while private files and normal execution stay on the user's machine.

HOW A COMPONENT ENTERS THE SYSTEM

  1. A developer publishes a component identity and a cryptographic fingerprint of its code.
  2. The developer creates a listing with a price, duration and transfer policy.
  3. A user chooses the component and reviews the permissions it requests.
  4. Solana records the purchase or time-limited license and settles payment.
  5. The local runtime downloads the artifact and checks it against the published fingerprint.
  6. Only then does Kernum mount the component inside its declared capability boundary.

This division is deliberate. Ownership and settlement need a shared source of truth. Private files, code execution and daily interaction usually do not.

WHAT OWNERSHIP MUST NEVER MEAN

A market inside a computer can easily become a worse version of the systems it claims to replace. Kernum must not turn identity, private keys, personal files, recovery rights or basic access to a user's own machine into products. A paid component must not receive silent authority over another component, and a transferable license must never imply transferable control of a person.

Ownership is useful only when it strengthens the user. Permission boundaries, local execution and the ability to remove or replace a component are not optional details; they are the point.

03 WHY I AM BUILDING AGAIN

Before taking a long break, I built another Solana experiment mostly for fun. It grew far beyond what I expected. The uncomfortable lesson was that attention followed the price more reliably than it followed the product. At a much larger market cap, the product did not have meaningfully more real users than it had when almost nobody was watching.

I cannot blame a market for noticing a market. If the technology was not useful enough to hold people's attention on its own, then it had not earned that attention. Price created curiosity; it did not create utility.

Kernum is me trying the opposite order. Start with a system worth understanding. Publish the implementation and its limits. Make one complete path work before describing a universe of future features. Let usefulness create the story instead of asking a chart to create it.

WHAT EXISTS TODAY

The repository contains a real local runtime, component manifest validation, code-hash verification, capability checks, a browser interface and an Anchor program for publishing components, creating SOL-denominated listings and recording licenses. The interface can run as a local demo, and the automated tests exercise installation, integrity checking, license decisions and marketplace account construction.

It is still early. The public catalog contains samples. The Solana program has not been presented as audited production infrastructure. The capability sandbox, recovery model and end-to-end deployment path need more work. I would rather state those limits plainly than hide them behind a polished roadmap.

WHAT I AM TRYING TO PROVE

The first goal is deliberately small: publish one real component, let a user understand its permissions, acquire the right to use it, verify its bytes locally and launch it without handing control of the machine to a storefront.

If that path can be made understandable and dependable, a larger system can grow from it. Developers could publish durable tools. Communities could maintain abandoned software. Agents could acquire narrowly bounded capabilities without receiving a user's entire wallet or filesystem. Interfaces could change while legitimate software rights remain portable.

If the small path does not work, none of the larger language matters.

WHY THIS IS PUBLIC

I do not want Kernum to become another project that survives only while its creator keeps every key and explains every decision. The code, assumptions and unfinished edges are public so the system can be judged by what exists. You can open the source beside this note, follow the component flow and see where the implementation stops.

I still hold plenty of reset buttons today. The point of building Kernum in public is to design a future in which the people using the computer hold more of them than I do.
